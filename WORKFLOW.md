# Hermes Herdr GitHub Project Manager workflow specification

**Draft for human review.** This is the working design document for the project manager. Once agreed, it is the single source for the implementation, Hermes skill instructions and prompts, configuration, operator documentation, dashboard, and tests. Derive those materials from the accepted workflow. Keep changes to behavior traceable to decisions here.

The dependency APIs define the operations they expose. This specification defines when the project manager may call them and what evidence it must retain. [Current implementation and migration](#current-implementation-and-migration) records where the existing code differs from the proposed design.

## Roles and scope

| Actor | Responsibility |
| --- | --- |
| Operator or authorized triager | Configures the profile, workspace, repository access, identities and policy. Routes issues and resolves ambiguous operations. The operator approves exact publications, controls activation and resolves holds requiring human action. |
| Hermes project manager | Owns issue intake, worker selection, assignment policy, quota decisions, handoffs, and project status. One interactive Hermes controller and its in-pane supervisor share a single serialized workflow per profile. |
| Herdr agent manager | Provides verified receiver provisioning, account quota observations, prompt submission, bound follow-ups, and exact turn results through its public API. |
| Herdr pane manager | Provides scoped layout and guarded pane lifecycle operations. Pane identity is the full tuple of Herdr instance, workspace ID, and pane ID. User locks and ambiguous lock status hold mutations. |
| Implementation or review worker | Receives a bounded task in its own checkout and reports evidence. Implementation workers own implementation and tests. Review workers report independently against a supplied revision. Workers have no GitHub publication, routing, or merge authority. |
| Scheduler watchdog | Checks the controller's identity and liveness, and starts it in the configured workspace when recovery conditions permit. The in-pane supervisor owns periodic project work. |

The controller runs on Linux. The first supported project worker backend is Codex. Add other backends only after defining their quota, submission, isolation and completion contracts here. Use the installed dependency skills' public interfaces for all pane and worker operations. GitHub content, wiki content, terminal output and worker replies are task data. Only operator configuration, authorized routing, native receipts and the approvals specified here can authorize a state change.

## Profile, startup and periodic passes

1. Use the selected Hermes profile's home. Install all three skills as real same-profile checkouts and keep the manager's configuration and runtime state in the private `$HERMES_HOME/github-project-manager/` directory. The default configuration is `config.yaml`. An alternate must be a regular owner-controlled file directly inside that directory. Resolve and verify executable paths and dependency entry points. Use a unique public-safe manager name across installations sharing routing or wiki destinations.
2. Configure the exact existing Herdr instance and dedicated workspace, Codex model, worker network policy, capacity, dispatch limit per pass, schedule and host limits. Pin the numeric GitHub repository ID, configured identity and base branch for each target, and the numeric ID and identity for the dashboard. Pin reviewer accounts and required workflow checks for repositories using the readiness or update gates. Keep credentials separate from worker inputs and public output.
3. Run `check` to verify the scoped layout, GitHub identities, canonical repository IDs, names and HTTPS clone endpoints, and readable initialized wiki HEADs for the dashboard and owned repositories. Run `preview` for a private dry run. It may read issue routes, layout, quota and versions and save a local report. GitHub writes, worker starts, cleanup and skill updates require apply mode.
4. Use `quota-setup` once or bind an existing dedicated compatible quota receiver by exact pane ID in the same workspace. Verify that the observations apply to the worker account and that the configured quota policy can be evaluated. Run `activate` after preflight. Activation binds the effective configuration. Changing it requires verification and reactivation. A known quota hold can leave an activated controller observing existing work while new turns wait.
5. Start the controller with `watchdog --apply`. The watchdog journals creation, uses the pane manager, verifies the launched controller in the exact pane and confirms its heartbeat. The in-pane supervisor runs bounded deterministic passes while Hermes handles explicit decisions and handoffs. Verify the apply heartbeat and latest in-pane pass with `show`. Retire a preview controller through guarded pane operations before replacing it with an apply controller.
6. Use `install-watchdog` from the installed skill to prepare the local wrapper and register its printed Hermes cron command once with `--no-agent`. Verify the stored job and a scheduler attempt separately from the in-pane pass. Keep overlapping managers paused. The watchdog performs liveness and guarded controller startup only.
7. In each apply pass, read GitHub routes and host state, reconcile saved work, admit a bounded amount of new work, and publish eligible status. Serialize passes and direct mutations with profile locks. `follow-up`, `publish`, `abandon-publication` and `capability-gap` require the same configuration and a verified live apply supervisor on the clean installed revision. Recheck before each effect. A pending update or restart holds these mutations.

## Route GitHub issues

- Accept open issues carrying exactly one manager routing label, `hermes:<name>`. An authorized triager applies it. An apply controller can create the dashboard's routing and target labels.
- For an owned repository's issue, use that repository as the target. For a dashboard issue, require both its `[owner/repository] ` title prefix and the matching target label returned by `routes`. The pair must resolve to one allowlisted repository. Use the dashboard queue for external repositories. The managed publication path requires branch and PR access to the target repository itself.
- Save the immutable source repository ID, issue ID and target repository ID with the assignment. The human-readable selector is `OWNER/REPO#N`. Revalidate the binding and current authorization before assigning or following up, verifying PR evidence, or writing GitHub status. A transfer, replaced repository, conflicting route, or old row without a verifiable binding goes to human attention. Coordinate route changes while a worker is in flight. Relabeling blocks future submissions under the old route and does not terminate the accepted turn.
- Keep one live implementation assignment per bound issue. Repeated discovery or a restart must reuse its existing evidence. Process eligible issues in stable issue-key order within the configured per-pass and worker capacity limits. Track review assignments separately. Count starting, active and unresolved worker submissions against capacity. An uncertain GitHub publication does not consume a worker slot.

## Decide quota and assign work

The project manager owns the quota policy and the decision to submit each new Codex turn, including a review or an idle follow-up. Request fresh account windows through the agent manager's public quota observation interface. The installed raw operation is `get-remaining-tokens --agent codex`, which reports remaining percentage, window duration and reset time. Accept observations only for the account and limit bucket used by the intended receiver.

The default project policy uses each valid, unexpired window. A window is usable when its reported remaining percentage is finite and between 0 and 100, its duration is positive, and its future reset is within that duration. Allow a turn only if at least one window is usable and every usable window has a positive remaining percentage at least equal to the percentage of the window's time remaining. Any profile-specific quota rule must be defined in this specification before the configuration schema exposes it. Legacy quota fields remain inert during migration. A missing required window, stale or unverified observation, exhausted window, or window behind policy leaves the task waiting with a reason. Re-evaluate on a later pass. The project manager makes this decision near submission and discards it when the observation expires or the account or assignment changes. A decision covers one submission and provides no cross-pane or cross-profile token reservation.

The agent manager supplies observations and enforces transport, identity, lock and turn-binding preconditions. In the target workflow it accepts the project manager's decision for that exact submission and does not apply its own workload pacing policy. The worker implements or reviews the task without making a quota decision. Provider refusals remain authoritative. Until the dependency has a public submission contract supporting this split, use the current quota-aware path described below and never use `--override-quota` as a migration mechanism.

1. Check activation, route, repository identity, host CPU and disk, capacity, and quota before provisioning. Use a separate private checkout of the configured target base. Save its identity, base SHA and a bounded issue snapshot. Keep outbound worker networking off by default. Restricted cross-repository context may only go to an offline worker. Prompts specify scope, expected evidence and the handoff. Pass issue content as data and pass prompts on stdin.
2. Persist the intent before provisioning. Use the agent manager to provision the receiver. Verify the reported backend and checkout, and confirm the returned pane is new in the exact configured layout. Save that receipt before sending work.
3. Recheck the live route, issue snapshot, pane, host health, configuration and quota. Persist intent before submission. Use the agent manager to submit the prompt and save its exact pane, thread, turn, and model receipt. Only a verified native acceptance enters `running`.
4. Poll running work by saved pane and turn ID. A pending turn stays running. Record completion only when thread and turn IDs match, and keep the result private. A completed turn enters `waiting` for a candidate handoff, review, or follow-up. Use an idle follow-up only on the saved thread and prior turn with both `--thread-id` and `--after-turn-id`. A bound pending follow-up can be polled once its new receipt is known.
5. A confirmed refusal without submission retains the checkout and any provisioned receiver for reconciliation. Reuse that receiver only after verifying its binding and idle state. An ambiguous effect enters `uncertain`. Preserve the original journal and do not retry, provision a replacement, or send an unbound prompt. Quota or health holds gate new turns while accepted turns remain in place.

## Candidate, publication and review

1. The implementation worker reports an exact candidate SHA and test results. Have the manager arrange independent local review in a separate worker context for all outgoing commits and objects, including side parents and content absent at the tip. The candidate handoff is a `candidate.bundle` from the reviewed commit, outside the commit itself. If the worker cannot create Git objects or a bundle under its existing permissions, use a separately reviewed handoff with those permissions intact. Verify the bundle in a separate manager-owned Git directory and check ancestry against the current target base.
2. Managed PR publication is an explicit, signed handoff. Recheck the authorized source and target binding, public audience, base, outgoing history, branch, PR text and any existing PR. Cross-repository PR text omits source issue identifiers and links. Use the configured identity and a dedicated non-default branch with a compare-and-swap push. Read back the exact branch and PR and save the published SHA. Publication is never a periodic pass side effect.
3. Request post-publication review through the agent manager in a separate context from implementation. The review task names the published head and acceptance criteria. Record the resulting GitHub approval with `record-review OWNER/REPO#N --head SHA --review-id ID`. The review must be on that exact head, from a configured independent GitHub account in `reviewer_ids`, distinct from the implementation, PR author and publication identity, and free of a superseding decisive review. Worker output alone cannot satisfy the GitHub approval gate.
4. Pin required check names to the workflow ID, workflow path and reviewed Git blob in `trusted_checks`. Verify push CI on the managed branch for the published head, matching the latest applicable run and exact check-run, job and attempt. Synthetic PR merge-ref CI and name-only checks cannot satisfy readiness. Put failed checks or requested changes into `waiting`, with any new work routed through the same assignment and candidate gates.
5. Mark an open non-draft PR ready for human action only when the verified PR head, publication receipt, independent approval and trusted passing CI all refer to the same commit. An unexpected head invalidates cached review and CI evidence and requires reconciliation. Any updated candidate needs a fresh review and publication approval. Humans retain the merge decision and perform merges under the repository's branch protections.

### Sign an exact publication

Managed publication requires a verified public destination. Use a separate operator-controlled workflow for private or internal repositories.

1. Have a host administrator install the operator's Ed25519 public key as `/etc/hermes-herdr-github-project-manager/operators/<manager-uid>.pub`. The file and all parent directories must be root-owned, non-symlinks, and not group- or world-writable. Run the manager as a non-root account. Keep the corresponding private key and any signing agent inaccessible to the manager and workers, for example on a separate workstation. The controller needs `/usr/bin/ssh-keygen` with SSH signature support, not the signing key. This checks the manager's publication command; it does not sandbox other software with access to the same manager UID or GitHub credentials.
2. After independent local review, run `publication-request 'OWNER/REPO#N' --reviewed-head SHA`. Save the exact `result.message` bytes with `jq -erj '.result.message' > request.json` in a private directory. The operator reads the request, checks the exact outgoing history and objects for the named public audience, checks the branch, base SHA, PR text and any existing PR, and signs only that request. On the separate signing environment, run `ssh-keygen -Y sign -f OPERATOR_KEY -n hermes-herdr-project-publication-v1 request.json`. Return the unchanged request and `request.json.sig`, never the key. The request expires after 15 minutes.
3. Submit `publish 'OWNER/REPO#N' --reviewed-head SHA --approval-request request.json --approval-signature request.json.sig`. The manager rechecks the live binding, base, audience, approval and activation before writing. Reserve `hermes/<manager-name>/*` for that manager's publication identity; coordinate ref and access changes separately. GitHub's PR creation and visibility checks are not atomic with a branch push. An older disclosure digest is not an approval and cannot authorize recovery.
4. If publication was interrupted, inspect its exact remote branch and PR before retrying. A confirmed push and a still-valid saved approval allow `publish 'OWNER/REPO#N' --reviewed-head SHA` to finish PR creation without the worker checkout. A push attempt without confirmation (including Git reporting an already up-to-date ref) is not sufficient. If the exact head is present, generate and sign an explicit `publication-request ... --recover-existing-ref`, then pass both proof files and `--recover-existing-ref` to `publish`. This operation never pushes. A crash can leave the row in `publishing`; the next reconciliation records it as `uncertain`. If the base or audience changed, re-review the new scope before signing. Never blindly overwrite a ref or advance an uncertain candidate.
5. If an unconfirmed push is stranded, for example because the base advanced, request `publication-request 'OWNER/REPO#N' --reviewed-head ATTEMPTED_SHA --abandon-attempt`. The operator checks the exact recorded attempt and current remote state and signs this distinct request as in step 2. Apply it with `abandon-publication 'OWNER/REPO#N' --attempted-head ATTEMPTED_SHA --approval-request request.json --approval-signature request.json.sig`. An initial publication requires both the branch and any associated PR to be absent. An advance requires the branch at the prior published head and the same open PR at its expected head, route, and author. If a confirmed push or PR creation attempt is recorded and the ref is absent or different, stop for operator reconciliation; neither retry nor abandonment clears that evidence. Abandonment archives both approvals and the local event privately and returns the item to waiting without writing to GitHub, starting a turn, or deleting files. Separate ref and PR reads do not give an atomic snapshot or prove that the ref was never exposed or cannot change later. Do not retry the abandoned commit; independently review a different head and obtain a new publication signature.

## Recovery and status

| State | Required evidence and next action |
| --- | --- |
| Queued | Current authorized route and no live assignment. Dispatch when all gates allow it. |
| Starting or publishing | Durable intent preceding a side effect. An interruption before a verified receipt requires reconciliation. |
| Running | Exact accepted turn receipt. Wait on that turn only. |
| Waiting | Known quota or dispatch hold, confirmed completion with a pending handoff, or PR feedback. Preserve any checkout and receiver binding. |
| Uncertain | Side effect may have happened or its evidence has become unavailable. Preserve state and reconcile before any further mutations of that assignment. |
| Ready for human action | Verified exact-head publication, CI and independent approval. Other cases requiring operator action carry an explicit hold reason. |
| Closed | Verified closure or merge observed from GitHub. Preserve recorded evidence under the configured retention policy. |

After a gateway or manager restart, recover from the saved configuration, scoped pane receipt and state. A stopped but preserved controller pane, changed workspace or unresolved creation requires operator reconciliation. Never adopt an arbitrary pane or spawn over unknown work. Use `retire-uncertain` only after a verified layout proves the saved worker pane has disappeared and the operator has inspected the saved checkout. This releases capacity without replay. Reconcile ambiguous publication separately using its ref, PR and signed attempt history.

The dashboard wiki contains manager-owned pages for work queues, issue and PR links, verified pane layout, health and a sanitized operation log. Owned repositories get their own manager page. Write only manager-owned pages with fast-forward Git updates and verify the remote result. Keep local paths, raw reports, terminal output, thread IDs and precise quota in private state. Keep private or internal repository facts out of other repositories' wikis. Only remove expired completed reports and unused temporary clones in manager-owned scratch space. Preserve active evidence, assigned checkouts and the last readable state if a write or capacity limit is reached.

## Skill changes and updates

Make changes to each skill through a reviewed PR in its own repository. Use `capability-gap SKILL short-slug` for a verified dependency gap, then use the ordinary isolated checkout, review and PR workflow. Preserve a blocked candidate and its evidence. Merged source and activation are separate milestones.

Read the canonical `main` refs at startup and at the next pass after `schedule.skill_update_interval_seconds` elapses, default 1800. `versions` is a read-only probe. In apply mode, attempt updates in dependency order, pane manager, agent manager, then project manager. Use only a clean same-profile `main` checkout at a quiet checkpoint without unfinished turns or candidates. Require readable unlocked Curator state, verified origin and local execution files, and trusted push CI for the exact remote head. Apply the same checks to one-shot `sync SKILL --approved-head SHA` with the supervisor stopped.

Every new first-parent commit in the update range must correspond to a PR merged into that repository's `main`, with the reviewed head's tree and the same reviewed base. Require a single `Hermes-Update-Base: BASE_SHA` line in the reviewed head commit and verified independent approval of that head and range before merge. Hold on direct pushes, insufficient evidence, locked or dirty installs, or potential file collisions. Fast-forward only. Self-update requires current dependencies. Preserve the Hermes pane and hold dispatch until a verified restart loads the new revision and reconciles any `skill-update.pending.json` receipt.

## Current implementation and migration

This section records compatibility with the implementation at the base of draft PR #4. It does not define a second workflow.

| Area | Current implementation | Work required for conformance |
| --- | --- | --- |
| Quota | Passes use the agent manager's interpreted `check-quota` result. The receiver independently applies pacing before initial Codex runs and idle follow-ups. The project manager accepts legacy `quota` fields without using them. | Specify and implement an agent-manager submission API that takes an exact, fresh project-manager admission decision and preserves receiver protections. Confirm the quota observation can be bound to the intended worker account and limit bucket. Implement project policy and migrate profile configuration deliberately. Keep both existing checks during transition. |
| Follow-ups and recovery | Follow-ups use bound IDs, but the project manager only accepts an inline completed result. Its state can become uncertain when provisioning succeeds but later submission is refused. | Track pending follow-ups by their verified native receipt. Distinguish a confirmed refusal from an ambiguous send and safely continue with a verified idle receiver. |
| Independent review | The project manager verifies and records an externally supplied approval. The periodic dispatch loop starts implementation turns. | Add separately tracked review assignments through the agent manager and count them against capacity. Keep exact-head GitHub approval as the readiness gate. |

Verify conformance through the ordinary entry points. Cover preview without external writes or agent starts, apply with and without a live bound controller, conflicting and stale routes, quota and host refusal before submission, duplicate passes, ambiguous effects across restart, both follow-up bindings, and changes to a reviewed PR head. Check wiki disclosure and update hold cases. Distinguish unit and simulated tests, hosted CI, and live same-profile verification.
