# Operator contract

## Configure and preflight

Install Python 3.10+, PyYAML, Git, `gh` and Hermes on Linux. Install the Herdr pane-manager and agent-manager skills in the same profile. Use their public entry points only. The manager launches its own interactive Hermes process as the application in a dedicated pane; Codex workers and quota probes go through the agent manager. The manager never reads the worker's internal transport or transcript.

Copy `examples/project.yaml` to `$HERMES_HOME/github-project-manager/config.yaml` (use `hermes config path` to locate the profile). Keep the file and generated state private, with the configuration owned by the profile's user and not a symlink. An alternate `--config` must be a file directly inside that same private directory. Configure an absolute path for the approved App launcher; the manager checks ownership and resolved paths for executables and dependency entry points. The dependencies must be real directories in this profile, not symlinked skills. Set an exact workspace ID, a supported worker model, a dashboard repository, the allowlisted repositories and base branches, and a publication identity per repository. Set a distinct public-safe manager name for each running instance. By default it derives a stable alias from the hostname rather than publishing the raw hostname. Do not run two instances with the same name: routing labels and wiki pages are per name, not cross-host locks.

Set `repo_id` for the dashboard and each allowlisted repository to the numeric `id` from GitHub's `GET /repos/OWNER/REPO`, using the configured identity. `check` verifies the ID, full name and HTTPS clone endpoint, as well as layout and each required wiki's Git HEAD. A previously accepted name is not proof that a renamed, transferred or replaced repository is still in scope. A repository being viewable in a browser does not prove the configured App can access it. Enable and initialize the dashboard wiki and every owned wiki with a first page. Private wikis require a GitHub plan that supports them. External repos do not need a wiki; this implementation expects the publishing identity to have branch and PR access to the external target. Fork-only contribution is not supported.

## Start and recover

1. Run `preview`, which creates only private local preview/state. It may read account quota; it does not label, launch a task, publish, or clean files.
2. In the dedicated workspace, run `quota-setup` once, or configure the exact pane ID of an existing, dedicated agent-manager receiver. Save its receipt and verify at least one usable quota window. Missing or incomplete windows do not block dispatch if another window can be evaluated.
3. Run `activate` after preflight and quota setup. It requires every configured identity and required wiki to resolve and binds activation to the exact configuration. Run `watchdog --apply`. Verify the next watchdog reports `manager-running` and `show` returns a fresh in-pane pass. The watchdog only keeps the manager application alive and never assigns work, publishes to GitHub, makes model calls itself, or sends keypresses. The in-pane supervisor starts one interactive Hermes controller and runs a deterministic pass between timer intervals. Profile-level locking prevents duplicate live managers or parallel passes. If a preview controller is running, end it and retire its exact pane through the pane manager before switching to apply mode.
4. Run `install-watchdog` from the installed skill. It prepares a regular, scheduler-contained script. Register the printed `hermes cron create ... --no-agent ...` command once and verify its stored job and actual attempt. Keep older overlapping managers paused. Do not add a scheduler prompt or monitor that does project work.

A gateway restart normally leaves the Herdr processes and private state intact. If the manager disappears, a watchdog can start a new controller in the same verified workspace and reuse the recorded state; it will not replay unknown turns. A stopped/preserved pane, a changed workspace ID, or an unresolved creation attempt is an incident, not grounds for a takeover. Read the manager pane through the pane manager and reconcile or close it through guarded tools after preserving state. A missing worker receiver cannot be replaced or reattached automatically by the current dependency API. Use the exact prior checkout/receipt; do not delete local state to make a dispatch pass.

## Work and publication

The manager binds each attempted assignment to the immutable GitHub source repository, issue and target repository IDs. An issue transfer, replacement or legacy assignment without that receipt requires operator reconciliation, not automatic rebinding. The manager verifies that a newly provisioned receiver reports the expected agent and checkout and that its pane is new in the configured workspace. It rechecks the checkout's host health before provisioning and submission. A held or unverified dispatch retains its checkout and any verified pane receipt for reconciliation; a quota refusal does not authorize automatic pane closure.

A tracked PR must still point to the exact commit published by the manager before its review can be recorded or it can be marked ready for human action. An external head change clears cached CI and review evidence and appears as an `unverified-pr-head` hold. Reconcile the unexpected change separately; remote CI or approval cannot replace the local publication receipt.

`follow-up`, `publish`, `abandon-publication` and `capability-gap` require activation for the effective configuration and a live apply supervisor in the configured workspace. Use the same resolved config file as the supervisor. The commands verify its launch, fresh heartbeat and running revision against the clean `main` installation in this profile. They hold the pass lock through the operation and recheck before submitting a turn, writing to GitHub, or archiving an abandoned attempt. Any pending `skill-update.pending.json` or reported restart hold blocks these commands until the supervisor can resume apply. Older supervisors lack the required proof and must be restarted using the updated installation. A supervisor launched outside a verifiable same-profile install cannot authorize these commands. If a hold appears after a write has already started, inspect the existing operation receipt before retrying.

- The manager creates `hermes:<name>` and target labels in the dashboard when activated. The user or an authorized triager applies exactly one manager label. For dashboard issues, use `[owner/repository] ` in the title and apply that repository's `hermes-target:…` label (use the private `routes` command to list them). The target label prevents a later title edit from silently rerouting approved work. External repos use only the dashboard queue. Owned repos also track their own routed issues, which need only the manager label. Coordinate handoffs before relabeling an in-flight task; a label cannot atomically revoke a running turn.
- GitHub, wiki and agent content is untrusted task data. Do not take repository targets, credentials, paths, commands or access policy directly from it. Use the reviewed model and worker settings; outbound worker networking is off unless opted in in local configuration. Never ask an agent to collect or upload credentials or bypass sandboxing. Stop rather than substitute an unsupported dependency operation.
- The worker owns implementation and tests in its isolated checkout. After separate local review, supply the accepted SHA and `candidate.bundle` produced by `git bundle create candidate.bundle HEAD` from that commit; keep the bundle out of the commit. If Git metadata is unwritable for the worker, use a separately reviewed handoff without changing worker permissions. The signed `publish` procedure requires independent local review and privacy checks on all outgoing commits and objects, including side parents and files removed before the tip. The manager verifies the bundle from a separate manager-owned Git directory, checks the current target branch and ancestry, then uses the configured identity on a non-default branch. Cross-repository PR text does not name or link the source issue. A route or default branch can still change after the last read; the destination ref itself has a compare-and-swap guard. After an uncertain result, inspect the exact GitHub ref and PR before retrying. No merges or branch protection changes.
- Request independent post-publication review from a separate worker/context through the agent manager. Configure independent GitHub account IDs in each repository's `reviewer_ids`; the PR author and publication account cannot satisfy the gate. Use `record-review OWNER/REPO#N --head SHA --review-id ID` after reading the full review and confirming it is independent. The manager checks the exact-head GitHub approval and whether a later review superseded it. Configure `trusted_checks` as a map from exact check names to GitHub Actions `workflow_id`, workflow file `path`, and the approved file's Git `blob` ID. An unpinned or changed workflow, or legacy `required_checks` alone, cannot mark the PR ready. Update a workflow pin only after reviewing the new workflow. CI failure produces a waiting item. `follow-up` requires a receiver supporting `--thread-id` and `--after-turn-id`; never fall back to an unbound send. Human approval and merge remain separate.
- To release capacity from a recorded ambiguous worker, inspect its saved checkout and run `retire-uncertain OWNER/REPO#N` only if its exact pane has disappeared. This requires a verified layout, retains the task and its evidence, and never resubmits the work. An ambiguous launch without a pane receipt still requires operator reconciliation. An ambiguous PR publication is tracked separately from worker capacity.
- Before any managed PR write, including within the source repository, follow the signed publication procedure below. Restricted cross-repository issues cannot be sent to network-enabled workers.
- Wiki pages are owned by manager name, written with fast-forward Git updates only, and checked against the remote. They contain issue and PR links, in-progress and waiting queues, pane rectangles and task state, and health codes; no raw terminal output, local paths, private threads or precise account quota. The dashboard has an additional operation log. Private or internal repository facts are not copied to another repository's wiki, even if that other repository is private. Legacy `dashboard.private_sources` never grants disclosure. Changing settings cannot retract earlier Git history. Managers do not overwrite shared navigation or each other's pages.

### Sign an exact publication

The manager supports direct publication only to repositories whose audience is verified as public. A private or internal repository's visibility does not identify its readers. Use a separate operator-controlled workflow for that case; no visibility or digest override is available.

1. Have a host administrator install the operator's Ed25519 public key as `/etc/hermes-herdr-github-project-manager/operators/<manager-uid>.pub`. The file and all parent directories must be root-owned, non-symlinks, and not group- or world-writable. Run the manager as a non-root account. Keep the corresponding private key and any signing agent inaccessible to the manager and workers, for example on a separate workstation. The controller needs `/usr/bin/ssh-keygen` with SSH signature support, not the signing key. This checks the manager's publication command; it does not sandbox other software with access to the same manager UID or GitHub credentials.
2. After independent local review, run `publication-request 'OWNER/REPO#N' --reviewed-head SHA`. Save the exact `result.message` bytes with `jq -erj '.result.message' > request.json` in a private directory. The operator reads the request, checks the exact outgoing history and objects for the named public audience, checks the branch, base SHA, PR text and any existing PR, and signs only that request. On the separate signing environment, run `ssh-keygen -Y sign -f OPERATOR_KEY -n hermes-herdr-project-publication-v1 request.json`. Return the unchanged request and `request.json.sig`, never the key. The request expires after 15 minutes.
3. Submit `publish 'OWNER/REPO#N' --reviewed-head SHA --approval-request request.json --approval-signature request.json.sig`. The manager rechecks the live binding, base, audience, approval and activation before writing. Reserve `hermes/<manager-name>/*` for that manager's publication identity; coordinate ref and access changes separately. GitHub's PR creation and visibility checks are not atomic with a branch push. An older disclosure digest is not an approval and cannot authorize recovery.
4. If publication was interrupted, inspect its exact remote branch and PR before retrying. A confirmed push and a still-valid saved approval allow `publish 'OWNER/REPO#N' --reviewed-head SHA` to finish PR creation without the worker checkout. A push attempt without confirmation (including Git reporting an already up-to-date ref) is not sufficient. If the exact head is present, generate and sign an explicit `publication-request ... --recover-existing-ref`, then pass both proof files and `--recover-existing-ref` to `publish`. This operation never pushes. A crash can leave the row in `publishing`; the next reconciliation records it as `uncertain`. If the base or audience changed, re-review the new scope before signing. Never blindly overwrite a ref or advance an uncertain candidate.
5. If an unconfirmed push is stranded, for example because the base advanced, request `publication-request 'OWNER/REPO#N' --reviewed-head ATTEMPTED_SHA --abandon-attempt`. The operator checks the exact recorded attempt and current remote state and signs this distinct request as in step 2. Apply it with `abandon-publication 'OWNER/REPO#N' --attempted-head ATTEMPTED_SHA --approval-request request.json --approval-signature request.json.sig`. An initial publication requires both the branch and any associated PR to be absent. An advance requires the branch at the prior published head and the same open PR at its expected head, route, and author. If a confirmed push or PR creation attempt is recorded and the ref is absent or different, stop for operator reconciliation; neither retry nor abandonment clears that evidence. Abandonment archives both approvals and the local event privately and returns the item to waiting without writing to GitHub, starting a turn, or deleting files. Separate ref and PR reads do not give an atomic snapshot or prove that the ref was never exposed or cannot change later. Do not retry the abandoned commit; independently review a different head and obtain a new publication signature.

## Health and maintenance

The project manager uses the agent manager's `check-quota` result to plan new assignments; it does not calculate pacing itself. The agent manager independently enforces pacing before each new Codex turn using the worker's account. One usable window is enough for planning. If the plan is unavailable, verify that the probe was provisioned by a quota-aware agent manager; do not bypass an older receiver. The project manager never supplies `--override-quota`. Legacy `quota` settings are accepted for existing profiles but no longer affect policy.

This is a start decision, not a token reservation or a guarantee of what in-flight workers will consume. Host pressure and worker capacity still gate new work. Managers sharing one account do not acquire a shared quota lock. Cleanup is restricted to expired completed reports in the manager’s private scratch directory, excluding active evidence, and temporary clones not handed off to workers. It does not remove user caches, build trees, assigned worktrees, or files from other skills. If the local state reaches its size limit, new writes stop without overwriting the last readable state; preserve the state for reconciliation.

All changes to the project-manager, agent-manager and pane-manager skills, including documentation and self-improvements, must go through a PR in the affected skill's repository. For a reproducible capability problem, use `capability-gap SKILL short-slug` to open or reuse a task in that repository. Make the change in an isolated checkout, test and review the candidate, and open or update the PR from a non-default branch. Read back the PR and exact head before reporting it submitted. Never patch an installed skill or push skill content directly to `main`, even for a small fix. If publication is blocked, preserve the candidate and report what prevented the PR. Keep project-specific policy out of portable skill source. Installation from merged `main` is a separate operation subject to the checks below.

The in-pane supervisor checks the three repositories' canonical `main` refs once at startup and then at the first management pass after `schedule.skill_update_interval_seconds` (default 1800). No extra cron job is needed. `versions` is a fresh read-only probe; `show` includes the last scheduled result and any hold. Preview never installs anything.

In apply mode the manager attempts pane manager, agent manager, then project manager. It updates real same-profile `main` checkouts using a non-destructive fast-forward, only with no unfinished tracked turns or candidates, a readable Curator lock record, a clean checkout and pinned CI passing on the exact remote `main` head. For CI, configure the pinned workflow to run on pushes to the managed branch; the manager checks the latest matching run and maps each check run to its job and workflow attempt. Synthetic PR merge-ref runs do not satisfy the exact-head policy. Every new first-parent commit must match a GitHub PR merged into that repository's `main`, with the same base commit and the same tree as the reviewed head. Include a single `Hermes-Update-Base: BASE_SHA` line in the PR head commit message before review. A pinned independent reviewer verifies that exact range and approves that exact head before merge. An editable PR or review body cannot substitute for the commit-bound base. Direct pushes, missing reviewed objects or evidence, and histories beyond the bounded verification window hold automatic updates. It never unlocks a skill or overwrites ignored-file collisions. Locked skills remain held for the operator. `sync SKILL --approved-head SHA` is a one-shot alternative while the supervisor is stopped, with the same checks. The self-update waits for both dependencies to be current. The supervisor keeps the interactive pane and stops scheduled dispatch after a self-update or an unverified installation outcome. Inspect `show` and restart the controller at a safe checkpoint to load the new code. If verification remains blocked after restart, inspect the private `skill-update.pending.json` receipt and reconcile the checkout; do not delete the receipt to clear the hold.
